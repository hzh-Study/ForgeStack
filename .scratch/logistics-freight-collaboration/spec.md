# 物流货运协同平台

Status: ready-for-agent

## Problem Statement

货主找车、物流公司调度、司机现场执行目前主要靠电话与纸质单据：货源信息不透明，抢单靠口头确认容易出现一单两司；司机出发与到达没有统一凭证，签收单容易丢失；报销靠拍照发给公司，额度与审核过程无法追溯；平台方看不到完整链路，出现问题只能事后拼凑记录。业务方需要一个覆盖实名准入、货主发货、物流公司抢单派车、司机打卡签收、报销审核、消息提醒与平台监管的线上协同平台。

## Solution

在现有四工程脚手架上实现一个多端平台：

- 管理员使用后台管理端，负责入驻审核、账号停用启用、基础资料与全平台只读监管。
- 货主、物流公司与司机 Web 共用前台用户端，按角色呈现不同的业务菜单与数据范围。
- 司机小程序是司机的主要工作端，承担任务查看、自抢、出发/到达打卡、照片与签收凭证上传。
- 后端统一承载账号、实名、入驻、订单、运单、任务、打卡、报销、消息与监管数据，所有端共用同一套状态与规则。

按业务闭环分两期落地：第一期打通「实名入驻 → 货主发布 → 物流公司抢单 → 拆单/指派/自抢 → 出发与到达打卡 → 运单完成」最小闭环；第二期补齐报销与特殊审核、消息中心、管理员监管与基础资料维护。

## User Stories

1. 作为管理员，我想用手机号加密码登录后台管理端，以便只处理平台治理，不参与具体运输业务。
2. 作为货主，我想自助注册并完成实名自动校验，以便获得发布货源的基础资格。
3. 作为货主，我想提交企业主体资料、法定代表人实名信息和资质附件，以便通过入驻审核。
4. 作为货主，我想查看自己的实名与入驻状态，以便知道当前能否发布货源。
5. 作为物流公司，我想自助注册并完成实名与企业法定代表人校验，以便申请入驻。
6. 作为物流公司，我想提交主体资料并经管理员人工审核，以便进入订单池接单。
7. 作为管理员，我想查看实名校验结果与入驻资料并做出通过或驳回，以便只让合规主体进入平台。
8. 作为管理员，我想停用或启用任一角色账号，以便制止违规操作且保留历史记录。
9. 作为物流公司，我想创建旗下司机账号并录入实名、手机号、驾驶证号与有效期，以便司机以公司员工身份登录。

## Implementation Decisions

### 工程与端侧边界

- 四个工程保持独立：后端、后台管理端、前台用户端、小程序与 APP。
- 后台管理端只承载管理员；前台用户端承载货主、物流公司与司机 Web；小程序承载司机现场执行。
- 所有端调用同一套后端接口，角色与数据范围由后端强制校验，前端菜单只做呈现。
- 前端统一 JavaScript、Tailwind、Pinia、moment、echarts 与 aieditor；不引入 TypeScript。
- 后端沿用统一返回、全局异常、Sa-Token 与 MyBatis-Plus；不引入 Swagger/OpenAPI。

### 账号与角色

- 扩展现有账号角色枚举为管理员、货主、物流公司、司机四种，登录仍走统一登录接口，按账号角色识别端侧与权限。
- 每种角色使用独立的资料表，通过唯一账号外键与账号表一对一关联；角色专属字段不写进账号表。
- 全角色手机号加密码登录，不接短信验证码；司机由所属物流公司创建并设置初始密码，首次登录强制改密。
- 一个实名身份全平台只能绑定一个角色；企业实名身份与法定代表人个人身份相互独立，法人校验不占用个人角色名额。
- 货主与物流公司自助注册；管理员只创建管理员账号；司机只能由物流公司创建。
- 停用司机前校验无进行中任务；停用物流公司前校验无未完成运单；停用不删除任何历史。

### 实名与入驻

- 实名校验通过适配器接口接入，本期使用本地模拟实现；结果落库，记录通过与不通过原因。
- 实名信息一经校验通过不可修改；变更走停用旧账号并按新实名重新创建。
- 货主与物流公司入驻状态为待审核、已通过、已驳回；驳回必填原因并记录审核人与时间。
- 只有已实名且入驻已通过的主体才能发布货源、查看订单池与接单。
- 证件号在列表与公司视图脱敏为前 3 位加后 4 位，完整号码只对本人与管理员可见。

### 订单与有效期

- 发货单包含运费报价、多行货物明细、一个装货点、一个卸货点、约定提货时间、约定送达时间、有效期与备注。
- 地址结构化保存为省、市、区加详细地址；接单前只投影省市区概要。
- 订单状态覆盖草稿、待接单、已接单、待拆分/待派发、执行中、已完成、已撤回、已取消、已下架。
- 接单后订单记录继续承载运单身份并生成运单号；不另建运单记录，避免双写与状态分叉；任务通过订单关联。
- 有效期按发布时刻起算的小时制；默认 10 天，可调 1–30 天；提醒时点为 T-2 天、T-1 天、T-1 小时。
- 到期提醒与自动下架由定时任务扫描，按订单加提醒类型做幂等键；订单被接走、撤回、取消或下架后未到点的任务立即失效。
- 仅已下架订单支持一键重发；重发生成新订单、重置有效期与提醒记录、保留来源订单与重发次数；撤回与取消只能新建货源。
- 撤回复核：仅待接单可撤回；取消：接单后且全部任务未出发时，货主或物流公司均可取消，需原因、二次确认与通知。
- 接单前对物流公司的投影隐藏收货联系人、电话、详细地址与全部备注；接单后对接单公司及其承接任务的司机开放。

### 抢单与派车

- 订单池接单使用条件更新，仅当订单仍为待接单时更新成功；并发失败方返回已被接走。
- 公司任务池领取同样使用条件更新，仅当任务仍为开放自抢时领取成功。
- 拆单按货物明细整行分配，同一明细行不得跨任务；允许增量拆分，但任一任务出发前必须全部分配完毕。
- 任务状态为待指派、待执行、运输中、已完成、已终止；弃单与回收是留痕事件，不是终态。
- 未出发时司机可弃单、物流公司可强制回收，均需原因、二次确认与留痕；任务回到待指派，可重新指派或再次开放自抢。
- 指派后任务归属即锁定；司机端确认仅为知悉确认，不改变归属。
- 同一司机与车辆同一时间只能有一个运输中任务；指派、自抢与出发打卡三处都校验车辆可用状态与运输中占用。
- 任务未出发前可调整货物分配，需留痕并通知已被指派的司机；出发后锁定。
- 一名司机只隶属一家物流公司、只绑一台车；绑定调整仅在司机无进行中任务时进行并留痕。
- 司机与车辆创建时分别必填驾驶证号与有效期、行驶证号与有效期；证件照片选传。
- 物流公司取消订单的条件与货主一致：全部任务未出发；取消后未出发任务置为已终止。

### 打卡与签收

- 每个任务只有出发与到达两次打卡，先出发后到达，不可跳步。
- 打卡必须同时具备提交时间、当前位置与规定用途的照片；照片从相册选取，不校验拍摄时间地点。
- 出发打卡至少两张，用途分别为装货完成与车辆状态；到达打卡至少两张，用途分别为卸货完成与签收凭证。
- 20 分钟窗口以约定提货或送达时间为基准，只用于标记按时或超窗；首次打卡全天允许。
- 同一节点自首次提交起 20 分钟内可重复提交多版本，最后一版为有效版本，历史版本永久保留；此后锁定，仅可追加说明。
- 追加说明不修改原记录，记录追加人与时间，任何时间可追加。
- 位置记录经纬度；逆地址解析仅用于展示，未配置地图密钥时留空，不阻塞打卡。
- 打卡记录与照片不可删除、不可覆盖。

### 报销与额度

- 报销单只能在任务出发打卡之后创建，必须关联该运输任务；一个任务可多笔。
- 额度按司机加自然月配置，平台默认 5000 元/月，物流公司可按司机覆盖。
- 当月累计计入待审核与已通过，被驳回不计；驳回重提只按最新版本计一次；归属月份按费用发生时间。
- 额度变更只影响新提交的报销单；超限状态按提交时的累计与额度快照判定。
- 超限单仍可提交并进入特殊审核，由所属物流公司二次复核并填写审核说明；管理员不参与审批。
- 审核通过为终态不可撤销；驳回必填原因，司机可修改重提并保留历史版本与历史审核记录。
- 报销状态为待审核、已通过、已驳回；超限标记与审核说明分别留痕。

### 消息中心

- 消息分系统通知与站内消息；系统通知由业务事件产生，站内消息按会话组织且仅支持文本。
- 会话关系限定为司机与所属物流公司、货主与接单物流公司、管理员与各角色；不可跨公司或跨无关订单发起。
- 铃铛未读数为未读消息条数；打开会话即标记该会话消息已读；系统通知逐条标记已读。
- 未读数与消息列表按 30 秒轮询，不引入 WebSocket；进入会话立即拉取。
- 消息记录永久保留，记录发送方、接收方、关联订单或任务、内容、发送时间与已读状态；不提供已读回执。
- 系统通知至少覆盖接单、三次到期提醒、自动下架、重发、任务出发、到达签收、运单完成、取消、指派、领取、报销提交与审核、超限待复核、入驻待审核与实名异常。

### 管理员与数据保留

- 管理员对业务数据只读，不提供任何修改或删除业务记录的接口。
- 管理员可审核入驻、停用启用账号、维护基础资料与平台默认参数、查询全平台业务链路与操作留痕。
- 管理员可查看消息发送记录，但不能修改消息内容。
- 所有业务记录永久保留，不设过期、不自动清理；撤回、取消、下架与重发历史同样保留。
- 本期不提供垃圾信息清理与任何批量处理业务记录的入口。

### 文件与访问控制

- 现场照片、签收凭证、资质附件统一走本地上传，单文件不超过 10MB，支持 PDF/JPG/PNG。
- 文件读取通过后端鉴权接口按角色与数据范围校验，不暴露公开静态目录；未授权统一返回无权限。
- 上传仅返回相对路径；访问图片时再由鉴权接口产出内容，不直接使用静态 URL。

### 接口与数据契约

- 后台管理接口统一使用管理端前缀，业务接口统一使用用户端前缀；分页统一使用页码与每页条数，返回统一结果结构。
- 身份与入驻：实名提交与查询、入驻资料提交与查询、管理员入驻审核与账号停用启用。
- 货主：草稿保存与编辑、发布、撤回、取消、一键重发、我的订单列表与详情。
- 订单池：公开列表与详情、筛选排序、接单。
- 物流公司：运单列表与详情、拆单与货物分配、任务指派、开放自抢、回收、货物调整、取消订单、司机与车辆管理、绑定调整、报销审核与特殊审核。
- 司机：任务列表与详情、公司任务池列表与领取、指派知悉确认、弃单、出发打卡、到达打卡、追加说明、报销提交与重提、我的记录。
- 消息：未读数、通知列表、会话列表、会话详情、发送消息、标记已读。
- 管理端：全平台监管查询、基础资料维护、平台参数维护、操作留痕查询、消息记录查询。
- 所有写操作返回统一业务错误码；并发冲突、状态不允许、权限不足分别返回可区分提示。

### 数据模型与约束

- 账号与角色资料：账号表沿用现有结构；新增货主、物流公司、司机资料表，均以唯一账号外键关联。
- 身份与入驻：实名身份表、入驻申请表；实名身份对证件类型与证件号建立唯一约束。
- 订单与货物：订单表、货物明细表、装卸货点表；订单保存运费、约定时间、有效期、状态、承运公司、接单信息、来源订单与重发次数。
- 任务与事件：任务表、任务货物关联表、任务事件表；任务事件记录指派、领取、知悉确认、弃单、回收、货物调整、出发、到达等留痕。
- 打卡：打卡版本表、打卡照片表、追加说明表；版本号、有效标记、按时标记与提交时间不可变。
- 报销：报销单表、报销版本或历史表、审核记录表；保存提交时累计与额度快照、超限标记、复核说明。
- 消息：通知表、会话表、会话消息表、已读状态；未读按消息统计。
- 监管与配置：操作留痕表、提醒发送记录表、基础资料表、平台参数表、司机月度额度表。
- 表名与字段名使用小写下划线；主键统一为 id；创建时间统一为 create_time；状态字段使用语义加 _status。
- 订单接单与任务领取使用数据库条件更新；运输中占用通过唯一激活键约束，保证一车一单。
- 所有金额使用 Double；所有时间按 Asia/Shanghai 解释，接口以标准时间格式传输。

## Testing Decisions

- 自动化测试只设一个 seam：后端 HTTP API。所有业务规则通过真实 HTTP 请求验证，不直接测试 Service 私有实现。
- 好测试只断言外部可观察行为：HTTP 状态与业务码、返回数据结构、隐私字段是否出现、状态流转后的再次查询结果、并发请求中仅一个成功。
- 测试覆盖模块：实名与入驻、订单与有效期、订单池抢单、拆单与派车、司机任务与打卡、报销与额度、消息未读、管理员监管、文件鉴权。
- 关键场景必须成组覆盖：并发抢单唯一、并发领取唯一、一车一单、超窗打卡仍可提交、首次提交后 20 分钟锁定、未出发弃单与回收、全部货物分配前不可出发、取消边界、报销跨月归属与驳回重提、超限快照、停用校验、隐私分级与证件号脱敏、未授权文件访问。
- 测试使用 SpringBootTest 与 MockMvc，连接独立测试库；每个用例通过接口或种子数据构造前置状态，结束后清理本次数据；不依赖执行顺序。
- 现有代码没有测试先例，需要在后端建立测试基类与统一测试数据构造器；后续所有业务模块复用同一 seam 与测试库。
- 三个前端不建立自动化 UI 测试；每个里程碑交付时用浏览器做冒烟验证，确认登录、菜单、表单与关键状态展示可用。

## Out of Scope

- 在线支付、运费结算、实际打款与发票；运费只作为报价记录与展示。
- 收货方独立账号与平台内电子签名；本期只上传收货方签字凭证照片。
- 运输轨迹回放、司机考勤统计、评价与投诉、多点装卸、多式联运、对账单导出。
- 站内消息的图片与文件收发、群聊、消息撤回、已读回执。
- 垃圾信息判定与清理、业务记录删除或批量处理。
- 真实第三方实名核验供应商、短信验证码、微信正式 appid 与地图服务密钥的生产接入。
- 物流公司员工子账号与权限分级。
- 前端自动化 UI 测试与端到端测试脚本。

## Further Notes

- 业务蓝本是已定稿的需求文档 v1.3；文件名仍保留 v1.0，正文版本以 v1.3 为准。
- 领域术语以仓库根目录的词汇表为准，实现中不得混用订单与运单、打卡与签收、弃单与取消等概念。
- 已记录的架构决策包括打卡窗口语义、实名校验适配器、任务弃单与强制回收、报销提交时点；实现不得回到这些 ADR 之前的旧口径。
- 第一阶段交付必须能跑通一条完整链路：管理员审核通过 → 货主发布 → 物流公司抢单 → 拆分并指派或自抢 → 司机出发与到达打卡 → 运单完成。
- 第二阶段再补报销、消息、监管与基础资料；两阶段共用同一套状态机与数据模型，不重复建模。
